# 共享浏览器池 + Playwright MCP + TG 一键接管：可行性评估（2026-10-22）

用户设想：维护一个浏览器池，提供 Playwright 全部能力的 MCP 给所有会话使用；会话里遇到登录等需要人的步骤时，TG 里出现按钮，点开进入 noVNC 直接操作这个浏览器。用户定位：code-anywhere 的产品能力，有竞争力。

## 结论

技术上可行，组件都是现成的。最大的前提不在技术：**手机要能访问到这台服务器**。其次是安全（noVNC 链接等于把已登录的浏览器交出去）和资源（本机浏览器进程已经超过阈值）。

## 本机现状（只读核查）

- 已装：Xvfb、x11vnc、websockify、`/usr/share/novnc`；Playwright 浏览器缓存（chromium 1243/1248、headless shell、webkit）；npx 可用，可直接跑官方 `@playwright/mcp`。
- 已有零散浏览器：一个 docker 容器里的有头 chromium 跑在 Xvfb :101，已运行 3 天，容器内 CDP 监听 0.0.0.0:38370；另有 Xvfb :99 和若干 headless shell。`browser-resource-check` 当前为 blocked（35 个浏览器进程 ≥ 32），可用内存约 6.4 GiB，总内存 15 GiB。
- 网络：服务器在内网（10.71.1.34），公网出口是 NAT（147.136.157.3），外部无法直接连进来。
- 先例：用户之前在 NAS 上用 noVNC 远程登录 SeaTalk（digital-buddy-ios 的 wiki 里有记录），说明这种用法用户熟悉。

## 建议架构

1. **池管理（桥接新模块）**：每个槽位 = 一个 Xvfb 屏幕 + 一个有头 Chromium（CDP 只监听 127.0.0.1）+ x11vnc + websockify。noVNC 需要屏幕，所以用“虚拟有头”，不能用真正的 headless。槽位数量小（2～3 个），空闲回收，接入 `browser-resource-check`，满了排队，不新开。
2. **浏览器 MCP**：和 local-sessions 一样做成每个会话一个 stdio 包装脚本。启动时按调用方 CLI 进程向桥接租一个槽位，然后启动官方 `@playwright/mcp --cdp-endpoint` 连上它，Playwright 的全部工具原样提供；进程退出就归还槽位。再加两个自有工具：`request_human_help(reason)` 和 `human_status()`。
3. **TG 接管**：会话调用 `request_human_help` 后，桥接在这个会话的 Thread 里发一条带按钮的消息：[🖥 打开浏览器] 和 [✅ 我弄好了]。打开浏览器的链接经桥接鉴权代理到这个槽位的 noVNC，链接一次性、短时有效。用户点“弄好了”，桥接通知会话继续。人操作期间锁住 MCP 的操作，避免人和模型同时点。
4. **登录态**：按“身份”保存持久 profile（例如 shopee-sso、seatalk），一次只租给一个会话；另提供干净的临时 context。

## 要注意的地方

1. **可达性（必须先定）**
   - 手机连公司 VPN 后能访问 10.71.1.34：TG 的普通 URL 按钮直接打开内网地址即可，最简单、也最安全。
   - 走公网隧道（cloudflared、ngrok 等）：等于把一个登录了公司 SSO 的浏览器暴露到公网，有合规风险，需要安全审批，不建议默认这么做。
   - Telegram Mini App（web_app 按钮，在 TG 内打开）要求公网 HTTPS，受同样的限制。
2. **安全**：noVNC 等于完全控制一个已登录的浏览器。链接要一次性、短时有效、绑定到具体槽位，只能经桥接鉴权访问；VNC、websockify、CDP 端口都只监听 127.0.0.1（现有那个容器把 CDP 开在 0.0.0.0，要避免）。profile 目录权限设为 600。好处是密码由用户在 noVNC 里自己输入，模型看不到。但模型截图可能拍到敏感信息，截图会进入 TG 和日志。
3. **资源**：本机已经超过浏览器进程阈值。浏览器池应当**替代**各会话自己启动的浏览器，而不是再加一份。否则只会更挤。有头 Chromium 每个约 300～800 MB。
4. **并发与隔离**：多个会话共用一个浏览器 context 会互相抢标签页、串登录态。所以一个槽位一次只租给一个会话。共用登录态方便，但会让不同项目串号，需要用户决定按什么粒度隔离。
5. **手机体验**：noVNC 在手机上能用，但屏幕小，需要缩放，软键盘要手动呼出。**中文输入法通过 VNC 基本不可用**；账号、密码这类英文输入没问题。**扫码登录**时二维码显示在手机屏幕上，同一台手机扫不了，需要另一台设备。Xvfb 分辨率可以设得适合手机，例如 1280x800，或者模拟手机视口。
6. **人机交接协议**：`request_human_help` 立即返回，会话用 `human_status` 查询或者等待通知，不能一直阻塞住工具调用（会超时）。用户点“弄好了”之后，用 send_message 或 urgent 通知会话继续。
7. **跨平台（产品化）**：Xvfb、x11vnc 只在 Linux 上有。macOS 上需要另想办法。长期更好的方案是**自建 CDP 屏幕流查看器**：通过 `Page.startScreencast` 推画面，`Input.dispatch*` 回传触摸和键盘。这样不依赖 VNC，真正的 headless 也能看，触摸映射对手机更友好，中文可以走网页输入框再插入文字。
8. **接入现有会话**：Claude 和 Codex 的 MCP 配置由 `./setup` 写入；已经在跑的会话要重启才能用上新工具（和 local-sessions 一样）。

## 分期建议

- **第一期（Linux，noVNC）**：池管理 2 个槽位、浏览器 MCP 包装、TG 按钮 + 鉴权代理 + 一次性链接、资源检查联动；实测一个会话在用户协助下完成一次真实登录。
- **第二期**：自建 CDP 屏幕流查看器替代 noVNC（跨平台、对手机友好、支持中文输入）；做身份 profile 管理；`./setup` 自动安装依赖。

## 待用户决定

1. 手机能不能连 VPN 访问这台服务器的内网地址？如果不能，走公网隧道是否可以接受、要不要走安全审批？
2. 登录态怎么隔离：所有项目共用一个身份，还是按项目或按身份分开？
3. 池子大小（建议 2 个），以及是否同意逐步收编现有那些零散的浏览器。
